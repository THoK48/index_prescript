# Personal Execution Tool MVP Plan

## Goal

생각하기 싫을 때 현재 해야 할 행동 하나를 결정해 주는 개인용 실행 도구를 만든다. 화면에는 ACTIVE 지령 하나만 표시하고, 완료 또는 실패로 종료된 뒤에만 다음 지령을 계산한다.

## Product invariant

- 상태 흐름: `IDLE → ACTIVE → COMPLETED | FAILED | INVALID → IDLE`
- `INVALID`는 Planner 품질 피드백이며 사용자 실패와 수행 진행도에 포함하지 않는다. `CANCELLED`는 중복 ACTIVE 복구 용도로 유지한다.
- ACTIVE 지령은 항상 최대 하나다.
- ACTIVE 상태에서는 다음 지령을 계산하거나 저장하지 않는다.
- 메인 화면에는 미래 행동 목록을 노출하지 않는다.
- Planner는 AI 없이 deterministic 함수로 구현한다.

## Scope

- Task, Routine, Schedule 모델과 로컬 CRUD
- 반복 일정과 반복 루틴
- 현재 시각, 마감, 가용 시간, 일정 충돌을 고려한 규칙 기반 Planner
- Task 진행 시간 누적
- 실패 이유를 반영한 재계획
- v0.1 저장 데이터 마이그레이션
- 도메인과 Planner 단위 테스트

## Non-goals

- 외부 캘린더, 지도, 길찾기, OAuth, 사용자 계정, 서버 DB
- LLM 기반 우선순위 결정
- 성공률, 레벨, 연속 기록 등 게임화

## Phases and gates

각 Phase 종료 시 `npm test`, `npm run typecheck`, `npm run build`를 모두 실행한다. 하나라도 실패하면 다음 Phase를 시작하지 않는다.

1. Ticket 용어와 데이터 마이그레이션
2. Task, Routine, Schedule 모델·반복 규칙·CRUD
3. deterministic Planner와 완료·실패 후 재계획
4. 실제 사용 흐름과 UI 검증

## Rollback

각 Phase는 앞 단계의 공개 타입과 저장 키를 유지하는 작은 변경으로 구성한다. 저장 데이터 변환에 실패하면 기존 키를 수정하거나 삭제하지 않고 오류를 표시한다.

## Acceptance checks

- 일정과 루틴, Task를 등록할 수 있다.
- Planner가 현재 조건에서 하나의 지령만 발행한다.
- 완료 시 Task 진행 시간이 누적된다.
- 실패 이유가 다음 Planner 입력에 포함된다.
- 새로고침과 v0.1 마이그레이션 후에도 기록이 유지된다.

## Planner observability and stale ACTIVE pass

### Phase 1 — 판단 기록

- Planner는 선택 결과와 함께 각 후보의 `SELECTED`, `ELIGIBLE`, `EXCLUDED`, `SKIPPED` 상태 및 근거를 반환한다.
- 지령 발행과 판단 기록 저장은 하나의 상태 전이에서 처리한다.
- 최근 기록은 `localStorage`에 최대 50건 보존하고 설정 화면에서 확인·복사할 수 있다.
- 기존 저장 데이터에 기록 필드가 없으면 빈 배열로 안전하게 마이그레이션한다.

### Phase 2 — 오래된 ACTIVE 처리

- 마감 경과, 날짜 변경 또는 장시간 방치된 ACTIVE 지령을 감지한다.
- 오래된 지령은 자동 완료·실패·삭제하지 않고 사용자에게 검토 창을 표시한다.
- 사용자는 현재 지령을 계속 수행하거나 `time_elapsed` 실패로 기록한 뒤 즉시 재계획할 수 있다.
- 이미 마감이 지난 Task가 새로 발행된 경우에는 발행 즉시 오래된 지령으로 오판하지 않는다.

이번 보완 작업은 사용자의 명시적 요청에 따라 검증 명령 실행을 보류한다. 테스트 케이스는 추가하되 `npm test`, `npm run typecheck`, `npm run build`는 별도 요청 전까지 실행하지 않는다.

## Reliability pass

### Phase 1 — 항목별 실패 cooldown

- Planner는 전체 지령의 첫 항목이 아니라 같은 source의 가장 최근 완료·실패를 확인한다.
- 일정 변경·몸 상태는 4시간, 장소·도구·시간 경과는 2시간 동안 `cooldownUntil`로 재발행을 보류한다.
- 다른 지령을 처리해도 cooldown이 사라지지 않으며, 같은 source가 이후 완료되면 과거 실패 영향은 끝난다.
- 시간 부족·난이도 실패는 같은 날 작업 단위를 줄인다. Planner 1차 개선 이후 기타 실패는 별도 감점 없이 마지막 선택 시각을 포함한 기본 정렬을 따른다.

### Phase 2 — 결정론적 System fallback

- 실행 후보가 없을 때 정리, 물 마시기, 걷기, 휴식, 스트레칭을 순서대로 발행한다.
- 완료·실패·이상 신고로 처리된 System fallback 수를 기준으로 선택하며 무작위는 사용하지 않는다.
- 기존 `reset-environment` 이력도 순환 횟수에 포함한다.

### Phase 3 — 데이터 백업과 복원

- 현재 `AppState`를 형식명, 버전, 내보낸 시각과 함께 JSON으로 내보낸다.
- 파일 다운로드와 클립보드 복사를 모두 지원한다.
- 선택한 파일은 즉시 반영하지 않고 파일명과 교체 경고를 먼저 표시한다.
- 파싱·마이그레이션·ACTIVE 정규화가 성공한 데이터만 `localStorage`를 교체한다.

## Planner 1차 개선

### 목표 및 범위

- 시간 실행 가능 여부와 우선순위 결정을 분리하며, 마감/중요도에 대한 가중치 계산을 제거한다.
- 기존 ACTIVE 최대 1개, 완료·실패 이력, cooldown, fallback 순환, localStorage 구조를 유지한다.
- AI, 대기 보너스 가중치, 외부 캘린더 또는 새로운 저장소는 추가하지 않는다.

### Phase 1 — 공통 가용시간

- `getAvailableWindow(now, schedules)`는 다음 고정 일정 시작 전 5분을 확보하고 정수 분 단위로 0~120분을 반환한다.
- 이전 공개 함수 `getAvailableMinutes`는 호환용으로 같은 함수에 위임한다.
- Task와 Routine은 공통 가용시간 안에서 최대 30분씩 수행하며 5분 미만이면 제외한다.
- Routine은 자신의 종료 시간도 함께 적용한다. 뒤쪽 고정 일정이 루틴 전체 구간과 겹쳐도 현재 실행 가능한 짧은 구간은 사용할 수 있다.
- 일정 수행 및 일정 준비는 자유시간 계산과 구분한다. 실패 후 축소는 원래 허용된 시간을 늘리지 않는다.
- 자유시간이 5분 미만이고 일정 준비도 실패로 보류되어 있으면 수행 작업 대신 수동 대기를 발행한다. 대기 이력은 기존 System 순환 횟수에서 제외한다.

### Phase 2 — 우선순위와 정렬

- 현재 고정 일정 → 15분 이내 준비 → 긴급 Task → 현재 Routine → 일반 Task → System 순환 순으로 선택한다.
- 마감 구간은 0=경과, 1=6시간, 2=24시간, 3=72시간, 4=168시간, 5=이후/미지정이다. 각 상한은 포함한다.
- 0~3 구간만 긴급 Task로 취급한다. 실행 불가능하거나 cooldown 중인 긴급 Task는 다음 계층을 막지 않는다.
- 같은 Task 계층은 마감 구간 → 중요도 내림차순 → 마지막 선택 시각 오름차순 → ID 순으로 정렬한다.
- 마지막 선택 시각은 기존 지령의 `createdAt`에서 계산한다. CANCELLED는 제외하고 이력이 없는 항목을 먼저 둔다.
- 같은 Routine 계층은 기존 우선순위 내림차순 → ID 순이다. ID는 기기 언어와 무관한 문자열 순으로 비교한다.

### Phase 3 — 판단 기록과 호환성

- 실제로 순서를 가른 조건을 선택 근거에 저장한다. 실패로 줄인 수행시간도 근거에 남긴다.
- 후보 기록에 선택 계층·마감 구간·중요도·마지막 선택 시각을 추가하되 기존 기록의 필드 누락을 허용한다.
- 기존 점수는 과거 이력 호환용으로만 읽으며 새 Planner는 점수 없이 선택한다.
- ACTIVE 상태의 추가 발행은 Planner를 실행하기 전에 거부한다. 완료·실패 이후 재계획은 기존 원자적 상태 전이를 사용한다.

### 확인 기준 및 실행 상태

- 경계 사례: 가용시간 4분/5분/120분, 자정 이후 반복 일정, 마감 구간 6/24/72/168시간의 양쪽 경계.
- 정렬 사례: 같은 구간에서 중요도 우선, 마지막 발행 시각과 완료 시각이 다른 이력, 미선택 항목, ID 동률 해소, 입력 순서 변화.
- 계층 사례: 일정 준비와 긴급 Task, 72시간 기준의 Task/Routine 전환, 실행 불가능한 긴급 Task, Routine 시간 축소.
- 보존 사례: 판단 입력 및 실패 축소 근거의 저장·백업·복원, 기존 ACTIVE 단일성 테스트.
- 관련 테스트 소스는 추가한다. 사용자의 검증 생략 요청에 따라 테스트·타입 검사·빌드는 실행하지 않는다.

### 복구 및 인계

- 되돌릴 경우 Planner/선택 기록 해석 코드만 이전 구현으로 복구한다. 저장된 완료·실패 이력은 삭제하지 않는다.
- 새 판단 필드는 선택 사항이므로 이전 저장 데이터는 그대로 읽는다. 선택 시각을 Task에 중복 저장하지 않는다.
- 비교용 폴더와 소스 ZIP에는 변경을 반영한다. APK 재빌드는 별도 요청 시 진행한다.
