# 짧은 Task 잔여량과 상세 루틴 단계 이어하기

## 1. 배경과 목표

사용자가 점검 항목 1·2의 수정을 요청했다. Task가 1~4분 남아 후보에서 빠지는 문제와, 긴 지속형 상세 단계가 일부 수행만으로 완료되는 문제를 해결한다.

## 2. 제외

점검 항목 3(겹친 고정 일정 선택)·4(보류 시 발급 연출)는 수정하지 않는다. UI·음원·우선순위 계층·서버·저장 키·APK·커밋·푸시는 변경하지 않는다.

## 3. 범위

공통 가용시간 최소 5분 정책과 잔여 작업량을 분리한다. 상세 루틴 지속형 단계의 완료된 블록을 회차별로 누적하고, 남은 시간만 다음 ACTIVE로 발행한다.

## 4. 입력과 의존성

기존 Task 진행량과 Ticket 이력을 사용한다. Routine 단계에는 별도의 전역 완료 카운터를 두지 않는다. 선택적 routineOccurrenceStartAt/EndAt과 routineStepCompleted를 Ticket에 추가하여 반복 회차와 블록 완료·단계 완료를 구분한다. 기존 Ticket은 발행 시각과 루틴 구간으로 해석한다.

## 5. 구현 순서

1. Task는 실제 가용시간이 5분 이상이면 남은 1~4분도 발행한다. 수행시간 0분·음수는 발행하지 않는다.
2. 순수 routineProgress 모듈에서 sourceType/sourceId/routineStepId/회차가 같은 COMPLETED 블록만 합산한다. 실패·무효·취소·ACTIVE·다른 단계·다른 회차는 합산하지 않는다.
3. 지속형은 목표 분량을 채워야 다음 단계로 넘어간다. 완료형·이동형은 완료 버튼 한 번으로 끝내 기존 의미를 유지한다.
4. 발행 시 원래 회차 구간을 보존하고, 완료 시 그 회차 기준으로 부분/최종 완료 여부를 함께 저장한다. 자정이나 루틴 종료 이후 완료해도 다음 회차를 막지 않는다.
5. 가용시간·30분 상한·피로에 의해 잘린 시간도 실제 완료 블록만큼 누적한다. 다음 지령은 남은 양에서 다시 제한한다. 계속 수행의 알림 연장은 수행량을 늘리지 않는다.
6. 기존 저장 이력·백업에서 진행을 복원한다. 회귀 테스트를 추가하고 테스트 → 타입 검사 → 웹 빌드를 통과한 뒤 인계한다.

## 6. 검증 기준

잔여 1~4분 완료, 실제 가용시간 4분/5분, 0분 제외, 60분 단계의 30+30분 수행, 피로 축소, 짧은 가용시간, 실패/무효/취소 배제, 단계/원본/회차 분리, 자정·늦은 완료, 다음 반복 회차, 완료형/이동형 한 번 완료, 백업 복원, ACTIVE 최대 1개를 확인한다. 두 차례 검증하며 실패가 있으면 다음 단계로 넘어가지 않는다.

## 7. 복구

원본과 이력은 삭제하지 않는다. 선택적 새 필드를 무시하는 이전 형식과 호환된다. 되돌릴 때 Planner의 단계 선택과 완료 시 메타데이터 처리를 함께 복구한다.

## 8. 위험과 대응

분량을 반복 템플릿에 누적하면 다음 날 진행까지 오염되므로 회차별 Ticket 이력에서만 계산한다. 완료형·이동형에 분량 누적을 강요하지 않는다. 기존 ACTIVE는 자동 교체하지 않는다.

## 9. 인계

검증 결과는 아래에 기록한다. 웹 소스에 반영하고 Android 설치 파일은 별도 요청 전까지 생성하지 않는다.

### 완료 결과 (2026-10-15)

- Task의 최소 가용시간 5분은 유지하며, 잔여 작업량 1~4분은 마지막 블록으로 발행한다.
- `routineProgress.ts`에서 반복 회차별 성공한 블록만 합산한다. 지속형 단계는 목표 분량을 채워야 다음 단계로 넘어가고 완료형·이동형은 한 번의 완료를 유지한다.
- Ticket에 발행 회차 구간과 단계 완료 여부를 보존한다. 구형 이력·백업 복원·자정 경과·늦은 완료 보고도 기존 데이터를 삭제하지 않고 처리한다.
- 회귀 테스트 13개 추가: 최종 106개 모두 통과. 최종 테스트 → 타입 검사 → 프로덕션 웹 빌드 두 차례 모두 성공했다.
- ACTIVE 최대 1개, 기존 완료·실패·무효 이력, 메인 화면과 음원은 유지했다. 점검 항목 3·4, APK 빌드, 커밋·푸시는 진행하지 않았다.
