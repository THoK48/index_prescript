# 이상 지령 피드백

## 목적

사용자 실행 실패와 Planner의 부적절한 선택을 별도 데이터로 기록한다. 이 단계에서는 사유를 축적하고 사례를 확인하며 Planner 규칙을 자동 수정하지 않는다.

## 상태와 저장

- `COMPLETED`: 정상 수행 결과. Task 진행 시간을 누적한다.
- `FAILED`: 지령은 유효했으나 수행하지 못한 결과. 기존 실패 정책을 사용한다.
- `INVALID`: 현재 상황에 부적절한 선택. `invalidReason`·`invalidatedAt`·`invalidDecision`을 보존한다.
- `CANCELLED`: 저장 데이터의 중복 ACTIVE 정규화에만 사용한다.
- `INVALID`에는 `completedAt`·`failureReason`을 기록하지 않는다. 완료·실패 집계와 Task 진행 시간은 바뀌지 않는다.
- 신고할 때 원래 Planner 판단을 Ticket 안에 보존하여 최근 로그 50건 제한 이후에도 근거가 남게 한다.

## 작업 단계

1. 상태 머신에 INVALID 전이를 추가하고 기존 완료·실패 정책과 분리한다.
2. 동일 sourceType/sourceId의 재선택 보류를 적용한 뒤 새 지령을 하나 발행한다. 기록과 재발행은 한 번의 저장 전이로 처리한다.
3. `i` 내부의 작은 신고 항목과 여섯 가지 사유 선택창을 추가한다. 주요 완료·실패 버튼은 유지한다.
4. 설정에 별도 품질 기록, 사유별 필터, 원래 판단과 JSON 복사 기능을 추가한다.
5. 이전 데이터 및 백업 호환을 유지하고 의미 있는 경계 테스트 소스를 추가한다.

## 사유

`TIME_IMPOSSIBLE`, `BAD_PRIORITY`, `ALREADY_DONE`, `CONTEXT_MISMATCH`, `TOO_REPETITIVE`, `OTHER`를 사용한다. 실패 사유 타입과 별도 관리한다.

## 재발행 정책

- Task·Routine·Schedule: 신고 시각부터 30분 동안 동일 원본의 재발행을 보류한다. 다른 항목을 하나 처리해도 보류가 유지된다.
- 실행 실패에 따른 시간 축소·보류 정책은 실제 COMPLETED/FAILED 이력에서만 읽는다. INVALID가 실패 사유를 대신하거나 기존 수행 실패 이력을 지우지 않는다.
- System: 신고도 순환 진행에 포함하고 직전 신고 항목을 즉시 재발행하지 않는다. 전체 fallback을 모두 장기간 잠가 행동 선택이 막히는 대신 순환을 계속한다.
- 가용시간이 짧은 대기 지령도 방금 신고한 원본과 다른 대기 행동을 선택한다.
- 저장 키와 백업 버전은 유지한다. 새 필드는 선택 사항이며 이전 기록의 필드 누락을 허용한다.

## 확인 사례

- INVALID가 FAILED 집계·진행 시간에 영향을 주지 않는가.
- 같은 제목의 다른 Task는 원본 ID가 다르면 선택 가능한가.
- 다른 sourceType에서 동일한 sourceId를 사용해도 서로 잠기지 않는가.
- 같은 항목의 30분 보류가 다른 지령 처리 뒤에도 유지되며 만료 후에는 정상 재계획되는가.
- Routine·고정 일정·System·짧은 가용시간 대기에서 즉시 재선택이 방지되는가.
- 중복·오래된 신고 요청이 새 ACTIVE 지령에 적용되지 않는가.
- 원래 로그가 정리되고 백업을 복원한 뒤에도 품질 사유와 판단 기록이 남는가.

## 실행 상태

관련 테스트 소스는 추가하되 사용자의 검증 생략 요청에 따라 테스트·타입 검사·빌드·브라우저 검증은 실행하지 않는다. 비교용 프로젝트와 소스 ZIP에 변경을 반영하며 APK는 별도 요청 시 갱신한다.

## 복구

UI와 Planner 선택 코드를 이전 구현으로 돌릴 수 있으나 저장된 INVALID 이력을 FAILED로 변환하거나 삭제하지 않는다. 기록은 그대로 보존하여 이후 개선 자료로 사용한다.
